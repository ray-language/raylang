# M93.2 — el framework web "a lo raylang" (especificación, PROPUESTA)

> **Estado: PROPUESTA — sin aplicar.** Diseño derivado del análisis contra la API de Express 5
> (<https://expressjs.com/en/5x/api.html>), con la directriz acordada: **no igualar firmas 1:1**,
> sino tomar cada funcionalidad y expresarla con los medios propios del lenguaje — errores como
> valores, enums + `match`, funciones de primera clase, UFCS, bounds, actores de heap aislado.
> El framework actual (M93, `packages/web/framework.ray`) se conserva como base; aquí se
> especifica lo que se añade y lo que se cambia.

## 0. Principios de diseño

1. **Composición sobre registro.** Donde Express añade variantes de API (`app.get(path, mw1,
   mw2, h)`, `router.use`, `app.route()`), raylang tiene funciones de primera clase: un
   middleware por ruta es un **combinador** que envuelve el handler, no una firma nueva por verbo.
2. **Valores sobre control de flujo oculto.** El `next()`/`next('route')`/`next(err)` de Express
   es CPS con tres significados según el argumento. En raylang el paso de un middleware es un
   **enum que se ve** (`Step.Next` / `Step.Done`), y el trabajo "después del handler" es una
   cadena explícita (`after`), no un envoltorio implícito.
3. **La respuesta es datos.** `Res` es un struct mutable que las fases rellenan en orden
   (mounts → pre → ruta → 404/405 → after). Cada fase ve lo que dejó la anterior. Sin
   `headersSent`, sin stream a medias: la respuesta se escribe UNA vez al final (esto ya es así).
4. **Lo que la stdlib ya resuelve no se reimplementa**: JSON = `std/json`, formularios =
   `std/url.parse_query`, cookies = `net/cookie`, correlación = `net/trace`, logging = `net/log`.
   El framework solo los **conecta** al contexto de la petición.
5. **Estado compartido = actores** (M38): el framework no ofrece `app.locals` mutable global
   (sería una mentira bajo heap aislado). El estado por-petición sí existe (`locals` en `Ctx`);
   el estado entre peticiones va por canales a una fibra que lo posee (documentado con receta).

## 1. Middleware (cambia la firma actual — ruptura aceptada, el paquete tiene días)

### 1a. El tipo `Step`

```raylang
/// What a middleware decides: continue the chain, or stop here (the response built so far is sent).
pub enum Step {
    Next,
    Done,
}
```

Reemplaza el `-> bool` actual de `use_mw`. Razones: se lee (`Step.Done` vs `false`), es
`match`-able, y deja sitio a futuros pasos sin romper (p. ej. `Step.Skip` si algún día hay
grupos de rutas). **Ruptura**: los middlewares existentes cambian `true`/`false` por
`Step.Next`/`Step.Done` (el paquete no está publicado; se migra el ejemplo y docs en el mismo
commit).

### 1b. Middleware por ruta: el combinador `with_mw`

Sin varargs ni sobrecarga, y sin duplicar los seis registradores de verbos: un middleware por
ruta es **composición de funciones**, no una API de registro.

```raylang
pub fn with_mw(mws: [fn(Ctx, Res) -> Step], handler: fn(Ctx, Res)) -> fn(Ctx, Res)
```

```raylang
app.GET("/admin/:id", with_mw([auth, rate_note], panel));
```

- Corre las `mws` en orden **con los `params` de la ruta ya capturados** (ventaja sobre la cadena
  global: `auth` puede leer `c.param("id")`); `Step.Done` corta y se responde lo que haya en `r`.
- Compone consigo mismo (`with_mw([a], with_mw([b], h))`) y con cualquier función `fn(Ctx, Res)`.
- Cero cambios en `Route`/`dispatch`: el enrutado sigue viendo un handler ordinario.

### 1c. Middleware global por prefijo: `use_on`

```raylang
pub fn use_on(app: App, prefix: string, mw: fn(Ctx, Res) -> Step)
```

`app.use_on("/api/", require_token)` — como `use_mw`, pero solo corre si `path` empieza por el
prefijo. Es azúcar sobre la cadena global (se registra envuelto en el chequeo de prefijo).

### 1d. La cadena `after` (el "después" sin CPS)

El middleware envolvente de Express (medir, cabeceras comunes, reescribir errores) se cubre con
una **segunda cadena explícita** que corre tras el enrutado, siempre (también en 404/405), en
orden de registro:

```raylang
pub fn after(app: App, hook: fn(Ctx, Res))
```

```raylang
app.after(fn(c: Ctx, r: Res) {
    r.header("X-Frame-Options", "DENY");           // cabeceras comunes
    if (r.code >= 500) { r.html(pagina_error()); } // página de error propia
});
```

Un `after` ve el `code`/`body` finales y puede mutarlos. Con `locals` (§2b) cubre el patrón
pre/post (p. ej. `auth` deja `user_id`, un `after` lo loguea). Lo que NO cubre y se asume:
envolver con `try/catch` (raylang no tiene excepciones: un `panic` del handler lo captura el
webserver → 500; personalizar ESE 500 requeriría un hook en `net/webserver` y queda diferido).

## 2. Contexto (`Ctx`)

### 2a. Helpers de lectura (conectan la stdlib, no la reimplementan)

```raylang
pub fn header_of(ctx: Ctx, name: string) -> string        // "" si falta (headers ya en minúscula)
pub fn cookie_of(ctx: Ctx, name: string) -> string        // net/cookie.parse_cookies; "" si falta
pub fn form(ctx: Ctx) -> Map<string, string>              // cuerpo x-www-form-urlencoded (std/url.parse_query)
pub fn form_field(ctx: Ctx, name: string) -> string       // azúcar sobre form(); "" si falta
pub fn json_body(ctx: Ctx) -> Result<json.Json, string>   // std/json.parse sobre el cuerpo texto
```

Convención de ergonomía ya establecida en el paquete: los lookup devuelven `""` si falta
(`param`/`query` ya lo hacen); lo **falible de verdad** (parsear JSON) devuelve `Result` — errores
como valores, componible con `?` si el handler delega en funciones `-> Result`.

### 2b. `locals`: datos por-petición entre middleware y handler

```raylang
pub struct Ctx { method, path, params, req, locals: Map<string, string> }

pub fn put_local(ctx: Ctx, name: string, value: string)
pub fn local(ctx: Ctx, name: string) -> string            // "" si falta
```

`Ctx` viaja por referencia (semántica de structs): lo que un middleware escribe, el handler y los
`after` lo leen. Tipado `string→string` a conciencia (sin `Any` en el lenguaje): cubre ids,
flags y claves; un dato rico se recalcula o se pasa por su propia vía. Es el `res.locals` de
Express sin dinamismo.

## 3. Enrutado

### 3a. Catch-all `*resto`

Un último segmento `*nombre` captura **el resto de la ruta** (incluidas las `/`):

```raylang
app.GET("/files/*path", fn(c: Ctx, r: Res) { r.text(c.param("path")); });
// GET /files/a/b.txt → c.param("path") == "a/b.txt"
```

`match_route` acepta `path.len() >= pat.len()` cuando el último segmento del patrón empieza por
`*`, y une los segmentos sobrantes con `/`. Solo en posición final (validado al registrar:
`panic` con mensaje claro — error de programación, no de petición).

### 3b. `ALL` (cualquier método)

```raylang
pub fn ALL(app: App, pattern: string, handler: fn(Ctx, Res))   // método comodín "*"
```

En el enrutado, `rt.method == "*"` casa cualquier verbo. Mayúscula como los demás registradores.

### 3c. `405 Method Not Allowed` automático (mejor que Express)

Si ninguna ruta casó pero **algún patrón casa el path con otro método**, responder
`405` + `Allow: <métodos>` en vez de 404 (RFC 9110; Express responde 404, incorrecto). El
`static_mount` de M56.9 ya lo hace para estáticos — esto lo generaliza a las rutas. El `not_found`
custom sigue siendo solo para 404.

### 3d. Rutas regex (`std/regex` — CORRECCIÓN: sí existe, M29.1/M81/M59.2)

> Nota de proceso: la primera versión de este análisis descartó regex "por no haberlo en la
> stdlib" — falso. `std/regex` es un motor Pike VM completo embebido (registro en
> `src/stdlib.rs`; fuente `examples/stdlib/regex.ray`), con `compile -> Result<Regex, string>`,
> capturas y tiempo LINEAL garantizado (inmune a ReDoS — algo que Express, con backtracking de
> `path-to-regexp`, no puede garantizar).

Para lo que los segmentos no cubren (extensiones, validar forma del parámetro):

```raylang
app.GET_re("^/files/(.+)\\.(png|jpg)$", fn(c: Ctx, r: Res) {
    r.text(c.param("1") + " tipo " + c.param("2"));   // capturas por número
});
```

- El patrón se **compila UNA vez al registrar** (`regex.compile`; el `Regex` es un valor, M59.2)
  — patrón malformado = `panic` al arrancar con el error del compilador de regex (error de
  programación, no de petición).
- Las capturas se exponen como params numerados (`"1"`, `"2"`, …; std/regex no tiene grupos con
  nombre — si algún día los gana, `:nombre` regex y `param("nombre")` casan solos).
- Convive con las rutas por segmentos: se prueban en orden de registro, como todo.
- `Route` gana una variante (enum `Pattern { Segments([string]), Re(regex.Regex) }`) — el
  cambio más profundo de esta fase, pero contenido en `match_route`/registro.

### 3e. Sub-aplicaciones: `mount` (el Router de Express, sin tipo nuevo)

Un "router" ES una `App` que nunca escucha — cero tipos nuevos:

```raylang
var api = new_app();
api.use_mw(require_token);            // middleware del grupo
api.GET("/users/:id", user_handler);  // rutas relativas al mount

app.mount("/api", api);               // fusiona: GET /api/users/:id
```

`mount` es **fusión estática en el registro** (no toca `dispatch`): re-prefija los patrones de
las rutas y mounts estáticos de `api`, y envuelve cada handler con `with_mw(api.middlewares, …)`
— los middlewares del grupo solo corren para sus rutas, reusando el combinador de §1b. El
`not_found` del sub-app se ignora (documentado: el 404 es de la app raíz).

## 4. Presets (funcionalidad que yo añadiría — no está en Express core, pero es lo que todo servicio termina escribiendo)

### 4a. CORS

```raylang
pub fn cors(app: App, origin: string)   // "*" o un origen concreto
```

Registra dos piezas: un middleware que responde el **preflight** (`OPTIONS` con
`Access-Control-Request-Method` → 204 + `Allow-Origin/Methods/Headers`, `Step.Done`) y un
`after` que añade `Access-Control-Allow-Origin` a toda respuesta. Una línea para el caso que
hoy exige conocer tres cabeceras.

### 4b. Logging con correlación (extiende `log_requests`, sin API nueva)

`log_requests` adopta el `traceparent` entrante (`net/trace.from_headers`) y estampa `trace_id`
en la línea JSON (`net/log.with_trace`). Un servicio detrás de un gateway correlaciona gratis;
sin cabecera entrante se genera un trace nuevo. Cero superficie nueva: se enciende con el mismo
`app.log_requests()`.

### 4c. Cache-Control en estáticos

```raylang
pub fn static_files_cached(app: App, prefix: string, dir: string, max_age_s: int)
```

Como `static_files` + `Cache-Control: public, max-age=N` (hoy el llamador debe saber ponerla;
con ETag/304 ya servidos por M56.9, esta es la pieza que faltaba para estáticos "de verdad").

### 4d. Respuestas JSON tipadas (candidata, decisión de diseño)

```raylang
pub trait ToJson { fn to_json(self) -> string; }
pub fn json_of<T: ToJson>(res: Res, v: T)     // r.json_of(user) — bounds de M9.2, cero magia
```

Con impls para primitivos en el paquete. El usuario implementa `ToJson` para sus structs (o
compone con `std/json.stringify`). Un `@derive(ToJson)` sería la versión redonda pero es feature
de compilador (nivel `@derive(Eq/Show)`) → se anota en IDEAS.md, no bloquea esto.

## 5. Lo que se DESCARTA (y por qué)

| Feature Express | Decisión |
|---|---|
| `next()` CPS / middleware envolvente | **No.** Dos cadenas explícitas (`use_mw` + `after`) + `locals` cubren los casos reales sin control de flujo oculto. |
| Regex en rutas | **SÍ — reubicado a §3d** (la primera versión lo descartó por el dato FALSO de que no había regex en la stdlib; `std/regex` existe y es Pike VM lineal). |
| `app.locals` (estado global mutable) | **No.** Miente bajo actores de heap aislado (M38). Receta documentada: estado en una fibra + canales. |
| `req.ip` / `req.protocol` | **Diferido.** Exige exponer la dirección del peer en `std/net` + `webserver.Request` (toca fuera del paquete). Se hará cuando algo más lo pida. |
| Hook para personalizar el 500 de un `panic` | **Diferido.** El catch vive en el `try_join` de `net/webserver`; un `after` ya reescribe los `>= 500` propios. |
| `res.sendFile`/`download` | **Diferido a demanda.** `static_files` cubre el caso común; un `r.file(path)` puntual es trivial de añadir después. |
| SSE por el framework (`app.sse`) | **Diferido.** `listen` usa `serve` (peticiones parseadas); SSE necesita poseer la conexión (`serve_raw`). Mezclarlos merece su propio diseño. |
| Endpoint `/metrics` integrado | **Diferido.** `net/metrics.Registry` es estado entre peticiones → actor + canales; hacerlo bien (fibra contadora propia del framework) es un diseño en sí. |
